# План эксперимента

## Проверяемый вопрос

По заданию нужно проверить, что небольшой набор тестов находит замедления не хуже полного, но тратит меньше времени. В статье Selector экономит 92% времени проверок, это раздел 5.2 и таблица 4. Авторы получили эту цифру моделированием, а мы проверяем то же на реальных запусках на одном компьютере. Вопросы такие:

1. Какие тесты замечают какие замедления.
2. Отличает ли Validator из статьи замедленные запуски от нормальных и как это зависит от порога и силы замедления.
3. Сколько времени экономит набор тестов, который выбрал Selector, и не пропускает ли он замедления на новых запусках.

## Сравниваемые варианты и baseline

Baseline — запуск всех 8 тестов. С ним сравниваем такие наборы:

- выбор Selector по Algorithm 1 из статьи при допустимом риске p0 = 0 / 0,05 / 0,1 / 0,2
- лучший набор, найденный перебором всех 256 вариантов с тем же условием
- самый быстрый тест для каждой части компьютера
- случайный набор, который укладывается в то же время, что и выбор Selector, с усреднением по 100 повторам

Validator тоже сравниваем с более простым вариантом:

- V1, из статьи: считаем похожесть результата на нормальный по формуле 4 и Algorithm 2 из раздела 3.4 и объявляем замедление, если похожесть не больше α
- V2, правило variance из репозитория авторов: замедление, если медиана упала больше чем на θ

В каждом запуске выполняются все 8 тестов, поэтому все варианты сравниваются на одних и тех же данных. Время набора считаем как сумму среднего времени его тестов без замедлений.

## Данные или нагрузки

Внешних данных нет, нагрузку создают сами тесты. Каждый тест выдаёт скорость, поэтому у всех тестов больше значит лучше.

| Тест | Что проверяет | Что делает |
|---|---|---|
| `cpu_sha256` | процессор | считает SHA-256 от блоков по 64 КиБ |
| `cpu_matmul` | процессор | перемножает матрицы 256×256 |
| `mem_copy` | память | копирует массив 256 МиБ, как тест Copy в STREAM |
| `mem_random` | память | читает случайные элементы из массива 256 МиБ |
| `disk_fsync` | диск | пишет 4 КиБ и ждёт, пока данные попадут на диск |
| `disk_randread` | диск | читает случайные блоки по 4 КиБ из файла 256 МиБ в обход кэша |
| `net_throughput` | сеть | передаёт поток данных по TCP |
| `net_rtt` | сеть | гоняет по TCP короткие сообщения туда и обратно |

Один запуск состоит из прогона всех 8 тестов при одном замедлении или без него. Каждый тест сначала прогревается 0,05 с, а потом делает 5 замеров по 0,2 с. Раунд — это все виды замедлений и 3 нормальных запуска в случайном порядке. Первые раунды нужны, чтобы настроить Validator и выбрать тесты, остальные — чтобы проверить выбор.

## Конфигурации и план запусков

Ноутбук: Intel Core Ultra 7 165H, 62 ГиБ памяти, SSD, Ubuntu 22.04, Python 3.10. У процессора есть быстрые и медленные ядра, поэтому тесты закреплены за одним быстрым ядром, чтобы результаты не скакали. После каждого запуска с замедлением делаем паузу 5 с, чтобы система вернулась в обычное состояние. Ноутбук стоит на зарядке, других тяжёлых программ не запускаем.

| Серия | Что меняем | Сколько запусков | Зачем |
|---|---|---|---|
| S0 | ничего, только нормальные запуски | 15 | понять, насколько шумят тесты, и выбрать пороги α и θ |
| S1 | `cpu_quota` 0,5 / 0,8 / 0,95<br>`cpu_freq` 2000 / 3500 / 4500 МГц<br>`mem_high` 550 / 500 / 400 МиБ<br>`mem_uncore` 2400 / 1600 / 800 МГц<br>`disk_iops` 500 / 2000 / 8000<br>`disk_bps` 20 / 100 МиБ/с<br>`net_delay` 0,1 / 1 / 5 мс<br>`net_loss` 0,5 / 2%<br>`net_rate` 2000 / 500 Мбит/с | 24 замедления и 3 нормальных запуска в раунде, минимум 6 раундов | ответить на все три вопроса |
| S2 | число замеров 3 / 5 / 10 и длина замера 0,1 / 0,2 / 0,5 с | по 3 раунда S1 | понять, насколько можно ускорить тесты без потери точности |
| S3 | день | повтор S1 в другой день | проверить, не появляются ли ложные тревоги, если Validator настроен по данным другого дня |

Ко второй точке по пробным запускам уточним:

- силу замедлений, чтобы были и сильные, и слабые, где тест теряет 5–20%
- пороги α и θ: берём самые строгие, при которых ложных тревог на нормальных запусках не больше 5%
- длину и число замеров для дисковых тестов, потому что они шумят сильнее остальных
- нужны ли ещё два замедления памяти, которые действуют только на тесты: выключить аппаратную предвыборку на ядре с тестами или большие страницы памяти для процесса с тестами

## Метрики

| Метрика | Что это | Единицы | Как получаем |
|---|---|---|---|
| Результат теста | средняя скорость за один замер | зависят от теста | тест считает сам, пишем в JSONL |
| Время теста | сколько идёт тест целиком, в среднем по нормальным запускам | с | засекаем снаружи теста, пишем в JSONL |
| Шум | коэффициент вариации в нормальных запусках | % | считаем по замерам из JSONL |
| Изменение | медиана с замедлением, делённая на нормальную медиану | раз | считаем по замерам из JSONL |
| Похожесть | 1 − d₁, где d₁ — площадь между функциями распределения замеров и нормальных результатов по формуле 4 статьи | от 0 до 1 | считает Validator по замерам |
| Замедление проявилось | ограничение стояло, тест той же части компьютера потерял хотя бы 5%, p < 0,01 | да или нет | счётчики ядра из JSONL и критерий Манна — Уитни по замерам |
| Recall набора | в какой доле замедленных запусков сработал хотя бы один тест набора | % | считаем по решениям Validator |
| Ложные тревоги | в какой доле нормальных запусков сработал хотя бы один тест набора | % | считаем по решениям Validator |
| Время проверки | сумма времени тестов набора и экономия по сравнению со всеми тестами | с, % | складываем время тестов набора |

Каждый запуск записываем одной строкой в JSONL: замедление и его сила, время, все замеры, результаты самопроверки тестов, счётчики ядра и настройки сети.

## Проверка корректности

- Каждый тест в каждом запуске проверяет себя на известном ответе. Например, SHA-256 от строки `abc` должен совпасть с эталоном, произведение двух матриц 2×2 должно дать заранее посчитанную матрицу, а данные, переданные по TCP, должны совпасть по хешу. Запуски, где самопроверка не прошла, выбрасываем.
- Проверяем, что ограничение стояло. Для этого берём счётчики ядра: сколько раз процесс упёрся в квоту процессора, какая была частота ядра, сколько раз процесс упёрся в лимит памяти, какая была частота uncore, какие лимиты стояли на диске. Для сети смотрим вывод `tc`.
- Сравниваем с тем, что должно получиться по расчёту. Квота 0,5 должна замедлить тесты процессора примерно вдвое. Если снизить частоту с 4700 до 2000 МГц, тесты процессора замедлятся примерно в 2,4 раза. При лимите 2000 операций в секунду диск не выдаст больше. С задержкой 1 мс обмен по сети не может быть быстрее 2 мс, а с лимитом 500 Мбит/с поток не превысит 59,6 МиБ/с.
- Модульные тесты Validator: одинаковые выборки дают похожесть 1, замедление вдвое даёт расстояние 0,5, ускорение не считается замедлением, сильно выбивающийся нормальный запуск не портит эталон.
- Модульные тесты Selector: пример из раздела 3.3 статьи, а ещё проверка, что перебор никогда не находит набор дороже, чем Selector.

## Обработка и анализ

- Для каждого теста строим эталон по нормальным запускам из первых раундов.
- Вопрос 1: таблица «замедление x тест», в каждой клетке доля срабатываний и изменение медианы.
- Вопрос 2: как меняется похожесть с силой замедления. Recall и ложные тревоги при разных порогах для V1 и V2.
- Вопрос 3: таблица всех вариантов набора и график «время проверки — recall» для всех 256 наборов, на котором отмечены выбор Selector и лучший по перебору.
- Разброс показываем по повторам: для каждой цифры даём медиану, минимум и максимум. Ещё повторяем расчёт с другим делением раундов на настройку и проверку и смотрим, меняются ли выводы.
