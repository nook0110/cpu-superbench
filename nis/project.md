# Описание проекта

## Назначенное задание

[P06. SuperBench: упреждающая проверка вычислительной инфраструктуры](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p06-superbench.md). Статья: Xiong и др., [SuperBench: Improving Cloud AI Infrastructure Reliability with Proactive Validation](https://www.usenix.org/system/files/atc24-xiong.pdf), USENIX ATC 2024.

## Выбранный технический путь

Выбрали самостоятельную реализацию: код авторов не запускаем, метод пишем сами.

Репозиторий авторов [`microsoft/superbenchmark`](https://github.com/microsoft/superbenchmark/tree/2e2c52b80f4e084b6b8ebd4f6148e0f901a26f95) на версии `2e2c52b` почти целиком рассчитан на видеокарты. Для процессора в нём есть только обёртки над готовыми программами: STREAM, fio, Intel MLC, HPL и tcping. Алгоритмов Validator и Selector из статьи там нет.

Тесты пишем на Python по образцу STREAM и fio. Validator и Selector делаем по описанию в статье, а правило variance из репозитория авторов возьмём, чтобы сравнить с ним наш Validator.

Решили писать на Python, так как основную работу внутри тестов делают библиотеки на C (OpenSSL, numpy) и ядро Linux.

## Что будет сделано и как это проверить

1. 8 тестов, по два на процессор, память, диск и сеть. Каждый тест сначала проверяет себя на примере с заранее известным ответом. Результаты всех тестов сохраняются в одном формате, по строке JSONL на запуск. Как проверить: `python3 -m minisb check`.
2. 9 видов замедлений, по два для процессора, памяти и диска и три для сети. У каждого задаётся сила. Как проверить: та же команда с `--faults`. По счётчикам ядра Linux в результатах видно, что ограничение стояло.
3. Автоматическая проверка, что замедление заметно. Тест той же части компьютера должен потерять хотя бы 5%, и разница должна быть статистически значимой: p < 0,01 по критерию Манна — Уитни. Как проверить: в отчёте ко второй точке у каждого замедления будет отметка, проявилось оно или нет, и цифры, по которым это решено.
4. Validator из статьи. Как проверить: модульные тесты на простых примерах и сравнение с правилом variance.
5. Selector из статьи и полный перебор всех наборов тестов, чтобы знать лучший возможный ответ. Как проверить: модульные тесты, в том числе на примере из статьи.
6. Эксперимент: выбранный набор тестов против всех тестов. Сравниваем, сколько замедлений нашли, сколько было ложных тревог и сколько ушло времени. Как проверить: таблицы и графики будут в `nis/results.md` вместе с командами, которыми они построены.
7. Отчёт о том, какие тесты что замечают, где Selector ошибается и какие выводы нельзя переносить на настоящие кластеры. Как проверить: в отчёте на каждый из трёх вопросов плана есть ответ с цифрами из серий.

## Поддерживаемые сценарии

Стенд работает на одном компьютере. Тесты запускаются по очереди в одном процессе, привязанном к одному ядру. В каждом запуске включено не больше одного замедления, и оно действует, пока идут тесты.

| Что замедляем | Название | Как |
|---|---|---|
| Процессор | `cpu_quota` | процессу достаётся только часть времени ядра, cgroup `cpu.max` |
| Процессор | `cpu_freq` | снижаем максимальную частоту ядра |
| Память | `mem_high` | ограничиваем память процесса, и ядро вытесняет лишние страницы, cgroup `memory.high` |
| Память | `mem_uncore` | снижаем частоту uncore, то есть кэша L3 и шины, через которые процессор ходит в память |
| Диск | `disk_iops` | ограничиваем число операций с диском в секунду, cgroup `io.max` |
| Диск | `disk_bps` | ограничиваем скорость чтения и записи, cgroup `io.max` |
| Сеть | `net_delay`, `net_loss`, `net_rate` | добавляем задержку, теряем пакеты или ограничиваем скорость через `tc netem` |

Ограничить скорость памяти для одного процесса нельзя: для этого нужна технология Intel MBA, которая есть только в серверных процессорах. Поэтому скорость памяти снижаем через частоту uncore. Это ограничение действует на весь процессор, в том числе на другие программы.

### Возможное продолжение

- включать несколько замедлений сразу
- плавно наращивать замедление
- запускать сетевые тесты между двумя машинами
- учитывать при выборе тестов, что пропуск замедления обходится дороже ложной тревоги
- сравнить проверку по расписанию с проверкой, которая запускается чаще, когда замедления случались недавно

## Упрощения

- Настоящих поломок мы не воспроизводим, замедления искусственные. Ограничение процессора замедляет вообще все тесты, ограничение объёма памяти мешает дисковым тестам, а снижение частоты uncore задевает и передачу данных по сети. Поэтому выводы касаются только таких замедлений.
- Авторский Selector ещё решает, когда запускать проверку. Для этого авторы обучают модель на истории поломок. У нас такой истории нет, поэтому наш Selector решает только, какие тесты запускать.
- Нормальный результат теста авторы считают по многим серверам. У нас один компьютер, поэтому берём несколько нормальных запусков на нём. Такой эталон учитывает, как результаты меняются от запуска к запуску, но не учитывает разницу между машинами.
- Validator сравнивает замеры с нормальными по площади между их функциями распределения, это формулы 2 и 4 в разделе 3.4 статьи. Как перевести эту площадь в число от 0 до 1, в статье не сказано. Мы делим все значения на медиану нормального результата, тогда при замедлении теста в k раз расстояние равно 1 − 1/k.
- Тест `mem_random` на numpy меряет, сколько случайных чтений в секунду выдерживает память. Задержку одного чтения он не показывает, поэтому ко второй точке перепишем его на C.
- Всё запускается на ноутбуке, поэтому замеры шумят из-за нагрева и фоновых программ. Чтобы шума было меньше, тесты закреплены за одним ядром, а нормальные запуски перемешаны с замедленными.
